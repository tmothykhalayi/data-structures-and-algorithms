# Interview Preparation Guide

## Technical Interview Structure

### Typical Interview Format

1. **Introductions** (5 min)
   - Brief background
   - Recent projects

2. **Problem Statement** (5 min)
   - Interviewer explains problem
   - Ask clarifying questions

3. **Solution Discussion** (35-40 min)
   - Plan approach
   - Write code
   - Test and optimize

4. **Follow-up Questions** (5-10 min)
   - Discuss optimizations
   - Edge cases
   - Related problems

---

## The REACTO Method

### **R**epeat
Repeat the problem in your own words to confirm understanding.

### **E**xamples
Work through 2-3 examples, including edge cases.

### **A**pproach
Explain your approach before coding. Discuss trade-offs.

### **C**ode
Write clean, working code. Think aloud.

### **T**est
Walk through code with examples. Check edge cases.

### **O**ptimize
Discuss improvements. Analyze time/space complexity.

## During the Interview

### First 5 Minutes: Clarification
```
Example questions to ask:
- "Can the input be empty?"
- "Are there duplicates allowed?"
- "What's the expected size of the input?"
- "Should I optimize for time or space?"
- "Can I use extra space?"
- "Is the array sorted?"
```

### Planning Phase:
```
Template to explain approach:
"I'm thinking of using [data structure/algorithm] 
because [reason]. This would give us [time complexity].
Let me walk through an example..."
```

### Coding Phase:
```
Best practices:
1. Write helper functions
2. Use descriptive variable names
3. Add comments for complex logic
4. Think aloud while coding
5. Don't stay silent for too long
```

### Testing Phase:
```
Test in this order:
1. Given example
2. Empty input
3. Single element
4. Large input
5. Edge cases specific to problem
```

## Common Interview Scenarios

### Scenario 1: You're Stuck
- **Don't:** Sit in silence
- **Do:** Talk through your thinking
- **Ask:** "Could I get a hint?"
- **Try:** Start with brute force

### Scenario 2: You Find a Bug
- **Don't:** Panic or start over
- **Do:** Debug systematically
- **Say:** "Let me trace through this example"
- **Method:** Use print statements mentally

### Scenario 3: Multiple Solutions
- **Don't:** Jump to coding first one
- **Do:** Discuss trade-offs
- **Say:** "I see two approaches..."
- **Choose:** Ask interviewer's preference

### Scenario 4: You Finish Early
- **Don't:** Say "I'm done" and stop
- **Do:** Optimize and discuss
- **Suggest:** Additional features or edge cases
- **Analyze:** Time/space improvements

## Red Flags to Avoid

### During Interview:
- ❌ Not asking clarifying questions
- ❌ Jumping straight to coding
- ❌ Silent for long periods
- ❌ Giving up easily
- ❌ Being defensive about feedback
- ❌ Not testing code
- ❌ Not knowing complexity of solution

### In Communication:
- ❌ "I don't know" without trying
- ❌ "This is easy" (sounds arrogant)
- ❌ Criticizing interviewer's hints
- ❌ Not explaining reasoning

## Company-Specific Tips

### FAANG/Big Tech:
- Expect 45-60 minute coding rounds
- 1-2 problems per interview
- Focus on optimal solutions
- System design for senior roles

### Startups:
- More focus on practical coding
- May include pair programming
- Product sense important
- Culture fit matters more

### Mid-Size Companies:
- Mix of coding and behavioral
- May include take-home project
- Team fit is key
- Varied interview processes
